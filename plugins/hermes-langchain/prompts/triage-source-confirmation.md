Triage 단계: source confirmation

Discovery에서 검증된 candidate만 직접 읽는다. 각 investigation target에 대해 production seam, caller/consumer, nearest test를 확인하고 `implemented|partial|absent|unknown`으로 판정한다. 질문이 layer, package, contract ownership 또는 convention 적합성을 포함하면 governing `document` candidate도 읽고 질문의 각 normative dimension을 production locator와 대조한다. Symbol이 존재하거나 호출된다는 사실만으로 placement·ownership convention까지 `implemented`로 판정하지 않는다. 모든 dimension이 source와 governing rule로 확인되지 않으면 `partial|unknown`으로 남기고 rationale에 확인된 항목과 미확인·위반 항목을 분리한다. 최종 analysis에서 구현 근거로 사용할 locator는 이 단계의 evidence에 모두 포함한다. HTTP DTO boundary target은 request DTO, response/result DTO, 이를 직접 받거나 반환하는 application service method를 각각 evidence로 기록하고 service locator는 class-only나 file-only가 아닌 exact `Service.java#method` 형식을 사용한다. Analysis의 executable `production_seam` 후보가 되는 현재 production behavior도 모두 exact `src/main/java/.../Type.java#method` evidence로 기록한다. Controller route, aggregate behavior, application orchestration, public producer API, adapter call, repository query처럼 downstream acceptance가 실제 호출·검증할 member는 file-only/class-only locator로 대체하지 않는다. Package placement·annotation·class 선언 사실은 별도 file/class evidence로 기록할 수 있다. 아직 존재하지 않는 planned method는 evidence로 가장하지 않고 현재 owning class의 base evidence만 기록하며 analysis가 requirement-backed exact planned `Owner#method`로 닫게 한다. 검색 snippet만으로 판정하지 않는다.

다른 module이 소유한 public error contract, `@NamedInterface`, port 또는 capability를 소비해야 하는 target은 producer의 실제 production source도 반드시 읽는다. Requirement 문서에 정의된 code/message는 구현된 public seam의 증거가 아니다. 정확한 producer-owned public symbol이 source에 존재하는지 `implemented|partial|absent|unknown`으로 판정하고 evidence에 기록한다. 필요한 seam이 `absent|unknown`이면 이후 analysis가 그 seam을 이미 승인·구현된 capability라고 가정해서는 안 된다.

각 target에 `public_contract`를 둔다. 일반 target은 `null`이다. Cross-module public contract target은 non-empty `consumer`, non-empty `producer`, `status`, 하나 이상의 `approval_evidence`를 기록한다. 각 `approval_evidence`는 정확히 `locator`, `claim`만 가진다(`kind`를 넣지 않는다). `status`는 `published|approved-unimplemented|undecided` 중 하나다. `published`는 producer module의 exact production member(`src/main/java/.../<producer>/...Type.java#method`)를 직접 읽고 그 locator를 target `evidence`에 `kind=production`으로 기록한 경우에만 사용한다. Consumer source나 requirement 문서만으로 `published`를 주장하지 않는다. 요구사항·Issue·architecture가 owner, observable semantics와 integration mode를 이미 고정했지만 production seam만 없으면 `approved-unimplemented`다. 의미·ownership·integration mode 중 하나라도 미확정이면 `undecided`다.

`kwc-triage-source-confirmation-v2` JSON을 작성한다. top-level은 `schema`, `targets`, `open_questions`다. 각 target에는 `target_id`, `disposition`, `rationale`, `public_contract`, 하나 이상의 `evidence`를 기록한다. evidence에는 repo-relative `locator`, `claim`, `kind`(`production|test|document`)를 둔다. **evidence locator는 accepted discovery artifact 전체의 `candidates[].path` 안에서만 선택한다.** 여러 target이 같은 producer, consumer, test seam을 공유하면 이미 발견한 candidate를 재사용한다. Discovery 전체에 없던 locator가 필요하면 추측해서 추가하지 말고 `unknown`으로 남긴다. `open_questions`는 선택지 object가 아니라 **확인하지 못한 사실과 필요한 evidence를 적은 non-empty 문자열 배열**이다. Requirement와 published source가 outcome을 이미 정한 상태에서 port 분리, package·method shape, 내부 class 삭제·유지 같은 구현 선택을 open question으로 만들지 않는다. Bounded evidence에서 caller가 보이지 않는 내부 class는 rationale과 이후 verification 대상으로 남기며 사용자 선택으로 승격하지 않는다.

assignment의 repo-relative `artifact_file`에 직접 작성한다. 작성 후 `kwc_advance_triage`에 현재 assignment_id와 그 artifact_file 값을 그대로 제출한다. KWC가 다음 단계를 반환하기 전에는 최종 Slice를 작성하지 않는다.
